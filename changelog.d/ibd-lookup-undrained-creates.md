Changed

- **IBD lookup no longer reads parents that are still in the confirm pipeline.** A lookup wave left out of its `tx.head` read only the transactions created in the same wave. A parent created by an earlier wave whose block was not yet connected was read, missed in every sealed `tx.head` segment, and then bound by load from in-flight anyway. Lookup now keeps the txids of the blocks it has decoded above its last drain+fence snapshot and leaves those parents out too. In a control sync, 30% to 50% of the txids lookup read between heights 400,000 and 850,000 were such parents. The set is one fixed table of 8 MiB: 2^20 slots, each a 40-bit tag of a txid hashed under a random per-process key and the height that created it. A slot is reused once its height has drained, a full bucket gives up its oldest create, whose spends are then read from `tx.head`, and every re-arm zeroes the table. The set binds nothing: load binds these parents from in-flight as before. Two txids that share a tag answer as one, so the set can hide a parent that is already on disk. Load then reads that one parent from `tx.head`, binds it, and logs a warning with the block hash, the height, and the parent txid. The table's heap counts toward the 1 GiB accounted heap the in-flight pin window is sized against. `ibd: perf` gains `lookup_undrained_skip` and `conf_pipe.undrained_bytes`. In 20-minute runs at heights 861,000 to 902,000 on a build where the write thread was no longer the limit, such parents were 12% of the txids lookup read, and leaving them out took the lookup thread's work from 25.1 ms to 21.8–23.0 ms per block. Those runs kept the set as one hash set with per-height txid lists; the table has not been timed on a node.
